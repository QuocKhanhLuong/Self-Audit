## What repeats versus what is amortized

- Per physical batch: one data stack, one producer-loss call containing three producer forwards, one extra producer feature forward, one full-batch CPU feature transfer, and two student forwards/losses/backwards. With candidate workers, bank generation enters once through the batch API; with canonical bulk auditing, fitting/scoring enters once through `fit_many` and once through `score_many` for the flattened candidate set.
- Per unit/sample: fitting/selection validation, one feature-row index, one four-candidate bank, and one result-recording path. Worker mode may process units in bounded chunks, but each unit still receives its own bank.
- Per candidate: candidate construction/ontology materialization, and one logical fit/score. Bulk mode amortizes the API invocation across all `B*4` candidates; it does not remove the per-candidate hypothesis or result entries.
- Per accumulation group: optimizer validation, gradient unscaling/normalization, optimizer steps, gradient clearing, and `global_step` increment. Producer and each active student are separate optimizer groups.

The producer embedding is the principal reused tensor: one detached batch embedding is indexed by every unit's bank generation and is never recomputed per candidate. Student targets are stacked once per arm and reused only by that arm's one forward/loss call. The code does not expose the internal kernel/evaluation count of the observation owner beyond the `fit_many`/`score_many` API calls recorded above.

## Detachment and ontology answer

Candidate generation receives detached producer features in both paths: scalar `_generate_bank` passes `features.detach()` (`trainer.py:_generate_bank:1327-1329`), while worker payload preparation converts each feature row to detached CPU `float32` and the worker rejects `requires_grad` tensors before calling `generate_bank` (`candidate_execution.py:75-85,98-123`). `hypotheses.generate_bank` repeats the CPU `detach().to(float32).contiguous()` boundary (`hypotheses.py:486-493`). Ontology is called inside `generate_bank` through `resolve_roles` at `hypotheses.py:501-506,514-520,527-533,554-560`; the unresolved semantic-alternative branch uses `apply_alternative` at `hypotheses.py:542-548`.
